# 电商售后政策 RAG 知识库

一个能跑、能量化、代码量不到 800 行的 RAG 检索问答系统。全部离线运行，模型走本机 Ollama。

## 它解决什么问题

售后客服每天回答的问题高度重复：「退款多久到账」「生鲜坏了怎么赔」。
这类问题的答案写在政策文档里，但客服找不到、用户看不懂。

RAG 的做法是：把政策文档切碎存成向量，用户提问时先检索出最相关的几段，
再让模型**只根据这几段**回答，并标出引用来源。好处是答案可追溯、不会瞎编。

## 快速开始

```bash
# 1. 确保本机 Ollama 已启动，且已拉取两个模型
ollama pull embeddinggemma:300m-qat-q8_0
ollama pull qwen2.5:7b

# 2. 装依赖
pip install -r requirements.txt

# 3. 跑实验（首次要建向量缓存，约 1 分钟）
python run_experiment.py

# 4. 起服务
uvicorn app:app --port 8123
# 检索：http://127.0.0.1:8123/search?q=信用卡退款多久到账&k=3
```

## 实验结果（24 篇语料 / 51 条评测集）

评测方式：每条问题标注正确答案所在的文档，取前 10 个切片，**去重到文档级**计算指标。

| 切片 | 检索方式 | Recall@1 | Recall@5 | MRR | P95 延迟 |
|---|---|---|---|---|---|
| 250 字 | BM25 | 0.569 | 0.843 | 0.699 | 0.6 ms |
| 250 字 | **向量** | **0.784** | 1.000 | **0.880** | 0.3 ms |
| 250 字 | 混合 | 0.686 | 0.961 | 0.818 | 0.8 ms |
| 400 字 | BM25 | 0.608 | 0.882 | 0.714 | 0.5 ms |
| 400 字 | 向量 | 0.686 | 1.000 | 0.840 | 0.1 ms |
| 400 字 | 混合 | 0.686 | 0.980 | 0.811 | 0.7 ms |
| 600 字 | BM25 | 0.627 | 0.843 | 0.729 | 0.4 ms |
| 600 字 | 向量 | 0.627 | 1.000 | 0.807 | 0.2 ms |
| 600 字 | **混合** | **0.706** | 0.961 | **0.825** | 0.7 ms |

直问 vs 转述（同一批问题的两种问法）：

| 检索方式 | 直问 R@1 | 转述 R@1 |
|---|---|---|
| BM25（400 字） | 0.885 | **0.320** |
| 向量（400 字） | 0.731 | **0.640** |
| BM25（250 字） | 0.769 | 0.360 |
| 向量（250 字） | 0.885 | **0.680** |

同一批问题，只是换了种说法，BM25 的准确率掉一半以上。

## 重排实验（bge-reranker-v2-m3）

两段式：向量先召回 Top-10，再用 cross-encoder 对这 10 条精排。
`rerank.py` 直接用 transformers 加载 `AutoModelForSequenceClassification`，没有引 sentence-transformers。

| 切片 | 向量 R@1 | +重排 R@1 | 向量 MRR | +重排 MRR | P95（重排后） |
|---|---|---|---|---|---|
| 250 字 | 0.784 | **0.843** | 0.880 | **0.922** | 80 ms |
| 400 字 | 0.686 | **0.843** | 0.840 | **0.922** | 103 ms |
| 600 字 | 0.627 | **0.843** | 0.807 | **0.922** | 156 ms |

三个数字一模一样，第一反应是"脚本写错了"。所以单独写了 `_check_rerank.py` 验证：

- 重排分数的极差均值 **8.29**（最小 2.00、最大 14.47），说明打分确实在区分，不是常数输出；
- 三种切片选出的 Top-1 **文档**彼此重合 46–47 / 51 条，说明"哪个文档最相关"几乎是切片无关的；
- 剩下 8 条错的是同一批问题（跨文档歧义），换切片也救不回来。

所以 0.843 是真的：**重排把"排得准不准"这件事从切片手里接管了**，
切片长度对 R@1 的影响被抹平（从 0.627–0.784 收敛到 0.843），代价是 80–156 ms 延迟，
相对一次 4 秒的生成可以忽略，所以离线评测默认开着重排。
在线服务（`app.py`）为了不和本机的 7B 生成模型抢显存，仍走纯向量，重排留作可选开关。

## 五个结论

1. **向量检索的 Recall@5 恒等于 1.000。** 正确文档**永远**在前 5 里，但排到第 1 的只有 63%–78%。
   这半句很重要：说明瓶颈不在"找不找得到"，而在"排不排得准"——
   后面的重排实验正好验证了这一点：加上重排，R@1 直接从 0.627–0.784 提到 0.843。

2. **切片长度对两种检索的影响方向相反。**
   向量：250 字最好（0.784），600 字最差（0.627）——切片越聚焦，向量越不含糊。
   BM25：600 字最好（0.627），250 字最差（0.569）——切片越长，关键词密度越高。
   所以"最佳切片"取决于你用哪种检索，不存在一个通用答案。

3. **混合检索的收益取决于语料规模。**
   语料 12 篇时，混合全面劣于向量（0.889 vs 0.972）；
   扩充到 24 篇后，600 字切片下混合反超向量（0.706 vs 0.627），400 字下与向量打平（0.686 vs 0.686）。
   结论不是"混合更好"或"混合没用"，而是**小语料下 RRF 会稀释强召回源，语料变难后它的价值才显现**。

4. **延迟不是瓶颈。** 检索本身 0.1–0.4 ms，主要耗时在 embedding（约 3–8 ms，有缓存时接近 0）
   和生成（约 4 秒）。

5. **重排用延迟换精度，且顺手抹平了切片长度的差异。**
   R@1 从 0.627–0.784 收敛到 0.843，MRR 统一到 0.922，代价 80–156 ms。
   对"切片调参"这种容易陷入的细节，重排是一个更省心的解法。

## 已知局限

- 重排只在 bge-reranker-v2-m3 上跑过，没有对比更小的 reranker（如 MiniLM 级）在延迟/精度上的折中。
- 评测只看"检索到没检索到"，没评估"答案说得对不对"（引用正确率、拒答率还没量化）。
- 语料是我按真实政策文档的形态写的，不是真实企业语料，难度可能偏低。
- 评测集是我自己写的，存在"我按自己的语料出题"的偏差。
